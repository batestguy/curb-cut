PROJECT: Curb Cut — An Accessible, Zero-Cost Disability Data Platform for Nigeria
A full specification for an AI agent to execute end-to-end.

1. Problem Statement
Nigeria has an estimated 35 million persons with disabilities, yet the data ecosystem is fragmented across PDF reports, closed registries, and inconsistent survey microdata. The 2025 JONAPWD Assumptive Data report acknowledges that "reliable data remains one of the most significant gaps" and calls for "more robust national data systems, disability registries, and inclusive statistical frameworks." Policymakers, advocates, and researchers cannot easily query, compare, or visualize disability prevalence, poverty intersection, or accessibility gaps across states.

Simultaneously, data tools themselves are rarely accessible. Screen-reader users, keyboard-only users, and wheelchair users who rely on assistive technology are excluded from the very dashboards meant to serve them.

Curb Cut solves both problems with one platform: a zero-cost, end-to-end data system that unifies fragmented public disability data into an accessible, queryable interface — and publishes the accessibility layer as a reusable open-source Python package.

2. Expected Solution
A monorepo platform with six layers:

Layer	Artifact	Purpose
Accessibility	a11y-viz on PyPI	WCAG-compliant plotting wrappers, auto alt-text, colorblind-safe palettes
Ingest	Source-specific loaders	Extract JONAPWD PDFs, NBS microdata, Hugging Face datasets into a unified raw layer
Warehouse	DuckDB + dbt models	Transform raw data into staging and marts with parameterized prevalence models
Analysis	Causal inference module	Estimate disability–poverty effect using doubly robust estimation
Serving	FastAPI + OpenAPI	Expose marts as a documented, read-only public API
Presentation	Streamlit app + MkDocs	Accessible Explorer app consuming the API, with a data dictionary and methodology docs
The unifying principle: the a11y-viz package sits at the bottom, consumed by the API (alt-text in JSON), the Streamlit app (every chart), and the docs (every diagram). This makes accessibility architecture, not an afterthought.

Goal: Ship a focused, accessible plotting library to PyPI before building anything else. This is the load-bearing piece; it validates the accessibility thesis and produces a verifiable external artifact.

python

PHASE 3: Prevalence Module + Sensitivity Analysis (Week 5–6)
Goal: Rebuild the JONAPWD Assumptive Data methodology as a parameterized, reproducible model with sensitivity analysis.

Method:
JONAPWD applied a 15% global prevalence benchmark to NPC 2025 population projections. The module implements this as a parameterized function and stress-tests the assumption.

dbt models:

text
marts.fct_prevalence_sensitivity
  -- columns: state, disability_cluster, gender, prevalence_rate (10–18%),
  --          estimated_count, scenario_label
Sensitivity grid:

Scenario	Prevalence Rate	Rationale
Low	10%	WHO lower-bound estimate
Conservative	12%	Nigeria-specific survey-adjusted
JONAPWD baseline	15%	Global benchmark used by JONAPWD
High	18%	Upper-bound from household surveys
Deliverables:

transform/models/prevalence/ with parameterized models

A sensitivity table queryable from DuckDB

A written methodology note (Markdown) documenting the divergence between benchmark-based and survey-based estimates

Visualization of the sensitivity grid in the Streamlit app (Phase 4)

Free-tier check: All computation in DuckDB locally. No cloud services. $0.

Gate: A sensitivity table exists as a queryable artifact, and the methodology note is committed.

Improvements over prior plan:

Add a prevalence_rate seed table so the sensitivity grid is configurable without editing SQL.

Add confidence intervals using a simple Monte Carlo simulation over prevalence rate uncertainty (run in DuckDB with random()).

Compare against NBS MPI estimates where available (71% of individuals in households with a disabled person are multidimensionally poor vs. 62% without) .

PHASE 5: Causal Inference Module (Week 9–10)
Goal: Estimate the causal effect of disability on multidimensional poverty using NBS MPI microdata.

Method:

Treatment: Household has at least one person with a disability (binary)

Outcome: Multidimensional poverty status (binary or index)

Confounders: Age, household size, education, urban/rural, geopolitical zone

Estimator: Propensity score matching (PSM) with doubly robust estimation

Heterogeneity: Causal forest or meta-learners by state and disability type

Libraries:

pymatchit-causal for PSM (free, open-source)

DoubleML for doubly robust estimation (free)

econml for causal forests (free)

StatsPAI as an alternative unified toolkit

Data:

NBS MPI 2021 microdata (.dta files) — requires registration at microdata.nigerianstat.gov.ng. Verify access before Phase 5. If denied, fall back to Nigeria DHS or MICS 2021 child functioning module.

Deliverables:

packages/models/ with PSM and doubly robust implementations

A policy brief (Markdown → PDF via pandoc) with effect estimates, confidence intervals, and plain-language interpretation

API endpoint /poverty/effect?state=Kano serving the estimates

Explorer app page visualizing heterogeneous effects

Free-tier check: All computation local. Policy brief generated with pandoc (free). $0.

Gate: An effect estimate with confidence intervals and a written brief.

Improvements over prior plan:

Add a refutation step using DoWhy to test the robustness of the estimate to unobserved confounding.

Add a placebo test using a pseudo-treatment (e.g., random assignment) to validate the pipeline.

Report both ATT and ATE with standard errors.

Document the ignorability assumption explicitly and discuss its plausibility.

6. Free-Tier Operational Playbook
Risk	Mitigation
GitHub Actions minutes exhausted (private repo fallback)	Use public repo → unlimited. For private forks, keep CI lean: only run ruff + pytest on PR, not on every push.
HF Spaces requires paid plan for compute	Deploy Streamlit app on Streamlit Community Cloud instead. Use HF Spaces only for static docs. 
Render cold starts	Accept 30-sec cold start for portfolio. Add /health warm-up endpoint.
Neon scale-to-zero	DuckDB file in repo eliminates this. Only use Neon if DuckDB >50 MB.
LLM rate limits	Cache alt-text to disk. Use Gemini Flash (1,500 RPD) with Groq fallback (1,000 RPD). Batch requests where possible.
NBS microdata access denied	Verify access before Phase 5. Fallback: Nigeria DHS, MICS 2021.
dbt DuckDB limitations	Avoid Snowflake-specific SQL. Test dbt build locally before pushing.
Streamlit app sleeps	Accept 30–60 sec wake time. Document it in the app.
7. Agent Execution Instructions
Feed this entire document to the agent. The agent should:

Start with Phase 0 — bootstrap the repo, CI, and directory structure.

Execute Phase 1 — build and publish a11y-viz before touching any data. This is non-negotiable.

Execute Phase 2 — ingest two sources only. Do not add a third until staging models pass tests.

Execute Phase 3 — parameterize prevalence, run sensitivity, write the methodology note.

Execute Phase 4 — deploy API and app. The API must be live before Phase 5.

Execute Phase 5 — causal inference. Verify microdata access first.

Execute Phase 6 — docs, data dictionary, launch.

After each phase, update the README hero section with the new live link.

After each phase, write a short changelog entry.

Never introduce a paid service. If a free tier is insufficient, redesign the component to use DuckDB or a static file.

The agent should ask for human review at each gate. The gates exist because scope creep is the primary failure mode.
